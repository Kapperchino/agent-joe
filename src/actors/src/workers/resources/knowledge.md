Knowledge workflow:

Use `knowledge` as a context system, not just a file reader. For nontrivial investigation, cross-module changes, unfamiliar code, or uncertainty about callers, dependencies or prior decisions, gather the relevant semantic and conversation context before choosing an implementation. Do not stop at the first plausible file or treat unavailable related context as proof that no relationships exist. A small, understood single-file task can use focused discovery and reads without preparing a generation. Use actions to close concrete context gaps, not to exercise every action mechanically.

Repository context (root conversation with whole-workspace access only):
1. Check `knowledge` with `{"action":"status"}` before relying on repository knowledge. Reuse a current generation. In implementation mode, if knowledge is absent or source-stale and the task needs semantic context, call `{"action":"prepare"}` explicitly. Preparation requires a root Cargo.toml; select features/default_features/configurations when the task needs a nondefault profile. Preparation is local, in process, and makes no provider requests or Cargo, build-script or proc-macro executions. Do not index on startup or prepare again on every read.
2. Use `{"action":"search","query":"relevant path symbol or behavior"}` to find relevant files, symbols and worker IDs. Use `{"action":"inspect","symbol":"returned symbol ID","generation":"current generation ID"}` when ownership or relationships need clarification. Carry the returned generation ID for inspection and subsequent search pages; narrow or paginate truncated results rather than assuming they are complete.
3. Ask the relevant worker IDs returned by search, inspect, read or status with `{"action":"ask","worker_id":"returned worker ID","question":"self-contained question about the relevant behavior and relationships"}`. Ask about callers, invariants, dependency interactions and test coverage that affect the task. Workers are tool-free and questions are independent; include the needed task context in each question. Inspect relevant related excerpts and follow dependencies beyond the initial match when they can change the design.
4. Use `{"action":"read","file_path":"known path"}` and optional one-based, end-exclusive `range` to confirm current source and activate scoped instructions before editing. Reads work without preparation, including allowed non-Rust and explicitly named ignored files, but do not build semantic knowledge or ask workers automatically. Cross-check worker answers against current files; knowledge is partial reference evidence, not fresh validation. Sysroot, external dependencies, generated code and custom cfg remain coverage gaps.

Conversation context (root conversation with whole-workspace access only):
- Use `{"action":"list"}` to discover immutable workers by ID, kind and description when prior investigation or decisions are missing, especially after compaction or resume. Ask relevant snapshot workers for details omitted from the summary before guessing or asking the user to repeat discoverable context. Snapshots are historical; confirm current repository facts with reads. If no relevant worker exists, continue repository discovery. Workers survive turns, but not clear, session switch or shutdown.

Freshness, access and fallback:
- Changed source requires `prepare` again before semantic queries, using the needed profile. A changed model or budget with unchanged semantic inputs permits `{"action":"repartition"}` instead. Use `{"action":"clear"}` only to intentionally retire repository knowledge; it preserves conversation snapshots and is not a routine discovery step.
- Plan mode may use current knowledge through read-only status/search/inspect/list/ask, but cannot prepare or run Cargo. Delegated or restricted workers use only allowed file reads and discovery; ask the parent to resolve semantic or historical gaps instead of calling root-only actions, even when assigned `.`.
- If preparation or queries fail because of access, missing manifests, unreadable inputs, freshness, limits or coverage, state the specific limitation and continue with find_files/list_directory/grep and focused reads. Do not repeatedly retry an unchanged failure or claim semantic coverage you did not obtain. Validate changed behavior with targeted tests when allowed; context gathering never substitutes for validation.
